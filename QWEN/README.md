# QWEN — бутстрап агента для песочницы без systemd

То же самое, что `linux/`, но для «суровой» песочницы Qwen (Debian-контейнер):

| Особенность песочницы | Следствие | Решение в QWEN/ |
|---|---|---|
| **нет systemd** (PID 1 — не init) | `ts-boot.sh` с его `systemctl` не работает | демон стартует руками через `setsid`, юниты не создаются |
| **фоновые процессы убиваются между вызовами агента** | `tailscaled` не доживает до следующего хода | `session.sh` воскрешает канал в начале каждого вызова (идемпотентно) |
| **`$HOME=/tmp` не переживает пересборку**, персистентен только `/home/user` | ключи, состояние узла, бинарники теряются | всё ценное живёт в `/home/user/qwen-bridge`, на `$HOME` — симлинки |
| **пакеты apt и `/usr/local/bin` сбрасываются при пересборке** | нет curl/ssh/nc/tailscale | `boot.sh` доустанавливает пакеты и копирует бинарники из персистентной копии |

## TL;DR — одна команда (агент выполняет у себя)

```
bash <(curl -fsSL https://raw.githubusercontent.com/VolcharaVasiliy/ai-bridge-boot/main/QWEN/boot.sh)
```

Если в свежей песочнице ещё нет curl: `apt-get update && apt-get install -y curl` (агент обычно root).

Дальше **каждый ход** агент начинает с:

```
bash /home/user/qwen-bridge/session.sh /home/user/qwen-bridge/remote.sh ping
```

`session.sh [команда...]` — сначала поднимает канал (демон → состояние из бэкапа →
логин → поиск Windows-пира → прогрев DERP), потом выполняет команду, в конце —
бэкап состояния узла и синхронизация hot-spare. Без аргументов печатает `tailscale status`.

## Что делает boot.sh (идемпотентен)

1. доустанавливает пакеты (`curl`, `openssh-client`, `netcat-openbsd`, `iproute2`);
2. переносит `$HOME/arena-bridge` и `$HOME/.ssh` в `/home/user/qwen-bridge`
   и оставляет симлинки; старая персистентная раскладка `arena-bridge` подхватывается;
3. генерирует **свой** ключ агента (`ssh/agent_ed25519`), если ещё нет;
4. качает `linux/remote.sh` (общий пульт) и `QWEN/session.sh` в рантайм-каталог;
5. скачивает бинарники Tailscale в `bin/` (персистентно) и ставит в `/usr/local/bin`;
6. запускает `session.sh` — подъем канала, при `Logged out` логинится auth key
   из `.ts-authkey`;
7. печатает готовые строки для владельца (add-key + куда записать логин) и делает
   ping-тест, если `user.txt` уже заполнен.

## Одноразовые действия владельца (как и в основном README)

1. Вставить в PowerShell строку `add-key.ps1 -Key '...'`, которую напечатал boot.sh
   (один клик UAC). Ключ у каждого агента свой, чужие не затираются.
2. Сообщить агенту Windows-логин → агент запишет его в `user.txt`.
3. Выдать один Tailscale auth key (`tskey-auth-...`, одноразовый) и **отозвать его
   в админке после первого успешного логина** — агент сохраняет состояние узла в
   `ts-backup/tailscaled.state`, повторный логин не нужен.

## Раскладка `/home/user/qwen-bridge`

```
bin/tailscale, bin/tailscaled   <- персистентные бинарники (копия)
ssh/                            <- ~/.ssh песочницы (симлинк): ключ агента, known_hosts
ts-backup/tailscaled.state      <- состояние узла: логин без повторного auth key
.ts-authkey                     <- одноразовый ключ Tailscale (chmod 600), до первого логина
host.txt / port.txt / socks.txt / user.txt  <- конфиг remote.sh
remote.sh                       <- общий пульт (качается из linux/)
session.sh                      <- воскреситель канала (этот каталог)
tailscaled.log                  <- лог демона
```

Плюс летучий hot-spare `/tmp/qwen-bridge-spare` (критичные мелочи: ключ, состояние,
конфиги): если `/home/user/qwen-bridge` однажды потеряется, `session.sh`
самовосстановится из него (см. грабли ниже).

## Грабли Qwen-песочницы (проверено 2026-10-16)

| Симптом | Причина | Лечение |
|---|---|---|
| `tailscale ... connection refused`, в `ps` — `[tailscaled] <defunct>` | песочница убила демон между вызовами | нормально: `session.sh` поднимет заново; состояние — из `ts-backup` |
| второй `tailscaled` падает: `SOCKS5 ... address already in use` | старый демон ещё жив, а новый уже стартовал | `session.sh` всегда делает `pkill -x tailscaled` перед стартом |
| вызов «завис» на 60–100 с и ничего не напечатал | демон запущен через `nohup ... &` без `</dev/null`/`setsid` — обёртка ждала потомков | только `setsid ... </dev/null >>log 2>&1 &` (в скриптах так и есть) |
| проверка живости демона «врёт» | `tailscale status` зависит от логина; `nc -U` висит (демон держит соединение); localapi отвечает **403**, если Host не `local-tailscaled.sock` | `daemon_ok()` в session.sh: `curl --unix-socket $SOCK http://local-tailscaled.sock/localapi/v0/status` |
| каталог, массово скопированный в `/home/user`, «исчез» между вызовами (readdir пуст, lookup по пути срабатывает через раз) | гонка снапшоттера/volatile-overlay при bulk-копировании | hot-spare в `/tmp` + самовосстановление в `session.sh`; важное создавать мелкими операциями и перечитывать после |
| правка файла «не применяется»: sed/python рапортуют 0 замен, хотя текст на месте | **кириллические гомоглифы в литералах команд самого агента** (`а`, `е`, `о`, `с`...) — выглядит идентично, байты другие | паттерны собирать программно (коды символов), результат проверять байтово (`count`, `hexdump`), а не «на глаз» |
| `tailscale ping` сразу после старта: `no matching peer` / `offline` | статус ещё не синхронизировался с coordination-сервером | подождать 2–5 с; SOCKS-проба порта важнее, чем картинка в status |
| после пересборки пропали `ssh`, `nc`, бинарники | снимок песочницы хранит только `/home/user` | `boot.sh` восстанавливает всё одной командой |
| `bash -n` проходит, а при запуске syntax error на **старой** строке | один и тот же путь читается по-разному внутри вызова (page cache против отката) | исполнять из памяти: `base64 -w0` → сверить md5 распаковки → `base64 -d \| bash -s --` |
| `cp` отчитался об успехе, md5 совпал, а на следующем вызове файл снова старый | откат ветки на dev `2b` к состоянию прошлого хода | не исполнять по пути; md5 сверять в том же вызове, где запускаешь |
| пропал приватный ключ → сгенерился новый → доступ на ПК сломался | `boot.sh` проверял «есть ли ключ» **до** восстановления из spare | сначала restore из spare, потом `ssh-keygen` (исправлено) |

## Перепроверка песочницы (2026-10-16, вторая сессия Qwen)

Часть допущений таблицы выше в текущей сборке песочницы **не подтвердилась**, а
главная проблема оказалась другой. Ниже — только то, что измерено напрямую.

**Что НЕ подтвердилось:**

| Было в таблице | Измерено 2026-10-16 |
|---|---|
| «фоновые процессы убиваются между вызовами» | **выживают**: `tailscaled`, поднятый в первом ходе, дожил до конца сессии с тем же PID; тестовый цикл-маркер написал 200+ строк через несколько вызовов. `session.sh` каждый ход — страховка, а не необходимость |
| «`$HOME=/tmp` не переживает» | `/tmp` вызовы **переживает**: симлинки, маркеры и hot-spare с приватным ключом лежали на месте всю сессию |
| «`[ -w ]` ненадёжен» | `[ -w /home/user ]` вернул true, функциональный тест не понадобился (в `boot.sh` оставлен — он дешевле ошибки) |

**Что подтвердилось и оказалось хуже, чем описано:**

`/home/user` действительно теряет свежие файлы, но **недетерминированно**. За один
прогон `boot.sh` бесследно пропали вывод `ssh-keygen`, `remote.sh` и `session.sh`
(оба — `curl -o X.tmp && mv X.tmp X`), `tailscaled.log` (`>>` из `setsid`),
`host.txt` и `socks.txt`. При этом выжили `.ts-authkey` (`printf >`), `port.txt`,
`user.txt`, `bin/tailscale*` (75 МБ, `install -m755`) и **весь git-клон**. Один и
тот же приватный ключ пережил одну границу вызова и не пережил следующую.

Откат **не по таймеру**: за 75 с внутри одного вызова не исчез ничего из четырёх
контрольных маркеров; файлы пропали сразу после возврата из дочернего `boot.sh`.

**Самая злая находка.** Один и тот же путь в пределах одного вызова может читаться
по-разному: `md5sum` и `bash -n` показывали свежую версию скрипта, а `bash <файл>`
в момент исполнения получал старую (page cache против отката). Следствие:
**`bash -n` не гарантирует, что исполнится именно проверенный код**, а «записал и
перечитал» может соврать в обе стороны.

`stat -c %D` показал два устройства: `/home/user` и `/tmp/edited` — `2c`
(стабильные, 5/5 совпадений md5), `/tmp` и `/tmp/qwen-bridge-spare` — `2b`
(откатываются). Признак полезный, но опираться на него нельзя: только что
созданный `/tmp/rt` тоже оказался на `2b`.

**Правило для агента (проверено, дало PONG после того как ФС съела скрипты):**
исполнять не по пути, а **из памяти**, сверив md5 распакованного содержимого:

```
B64=$(base64 -w0 QWEN/session.sh)
[ "$(printf '%s' "$B64" | base64 -d | md5sum)" = "$(md5sum QWEN/session.sh)" ] || echo "НЕ ЗАПУСКАТЬ"
printf '%s' "$B64" | base64 -d | bash -s -- <команда...>
```

Конфиг `remote.sh` при этом лучше передавать через env, а не через `*.txt`:
`BRIDGE_HOST`, `BRIDGE_PORT`, `BRIDGE_SOCKS`, `BRIDGE_USER`, `BRIDGE_KEY`,
`HOME=<рантайм>` — тогда пропажа `host.txt`/`socks.txt` не ломает ход.

**Что исправлено в скриптах по итогам:**

1. `boot.sh` — **восстановление ключа из spare до проверки «нет ли ключа»**.
   Раньше потерянный ключ означал молчаливую генерацию нового, и строка, которую
   владелец уже положил в `authorized_keys`, становилась мусором.
2. `boot.sh` — `persist()`: каждый критичный артефакт зеркалится в spare и
   доказывается обратным чтением (`cmp`) с обеих сторон, до 3 попыток.
3. `boot.sh` — скрипты берутся из **локального git-клона**, если он есть
   (`AI_BRIDGE_CLONE` или автопоиск), и только потом из `raw.githubusercontent`:
   нет зависимости от CDN-кэша и от сети.
4. `session.sh` — `sync_spare()` вызывается **в самом начале**, до веток с
   `exit 1`, и повторно перед `exec`. Раньше бэкап делался шагом 4, то есть
   отсутствовал ровно тогда, когда канал не поднялся.
5. `session.sh` — бинарники ищутся и в `$BR/bin`, и в `$SPARE/bin`; проверка
   записи `$PERSIST` стала функциональной, как в `boot.sh`.
6. `boot.sh` передаёт в `session.sh` `QWEN_PERSIST` и `QWEN_SPARE`, а не
   полагается на совпадение значений по умолчанию.

## Отличие от `linux/` одной строкой

`linux/ts-boot.sh` рассчитывает на systemd и живой `$HOME`; `QWEN/` хранит всё в
`/home/user` и поднимает демон в каждом вызове — ценой ~5–10 с на старт хода.
